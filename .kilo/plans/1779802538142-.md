# Extending Herve with Time and Power Awareness via Microarchitecture Profiles for Code Profiling

## Overview
This plan outlines how to extend the Herve RISC-V ISS to be time and power aware by integrating the provided microarchitecture model format, enabling its use as a detailed code profiler. The goal is to enhance Herve with cycle-accurate timing, energy estimation, memory hierarchy modeling, and comprehensive event tracing to profile code performance and power consumption while maintaining backward compatibility.

## Current State Analysis
Herve currently:
- Tracks basic cycle count via `csr_mcycle` (incremented per instruction)
- Models functional behavior of RV32IM[C] instructions
- Provides DPI-C/VPI interfaces for RTL integration
- Has no pipeline, cache, or power modeling

## Proposed Architecture

### 1. Microarchitecture Model Integration
- Add JSON parser for the microarchitecture model format
- Create data structures to represent the model components
- Load model at initialization via new API or environment variable

### 2. Enhanced Timing Model
- Replace simple `csr_mcycle++` with sophisticated timing based on:
  - Instruction class latencies (ALU, MUL, LOAD, etc.)
  - Pipeline stall penalties (hazards, structural)
  - Memory hierarchy effects (cache hit/miss penalties)
  - Branch prediction penalties
- Model memory access timing with L1/L2/DRAM hierarchy
- Incorporate accelerator timing for vector operations

### 3. Power/Energy Modeling
- Track energy consumption per instruction class
- Model state power (active, idle, sleep states)
- Calculate total energy as sum of dynamic + static components
- Provide power estimation interface

### 4. Event Hook System
- Implement trace points as specified:
  - instruction_commit, memory_access, cache_miss, branch_mispredict, accelerator_call
- Attach PC, cycle, and energy information to events
- Enable/disable tracing via configuration

### 5. Accelerator Support
- Model vector/accelerator operations (RVV, GEMM, etc.)
- Provide hooks for accelerator timing and energy
- Support throughput and latency modeling for accelerators

## Implementation Plan

### Phase 1: Model Loading and Data Structures
1. Add JSON parsing library (e.g., jsmn or cJSON) or simple parser
2. Define C structs for:
   - MicroarchitectureModel (top-level)
   - CoreIdentity, ExecutionModel, MemoryHierarchy, PipelineModel, PowerModel
   - Accelerator, EventHooks
3. Add functions to load model from file/string
4. Modify initialization to accept model parameter

### Phase 2: Enhanced Cycle Counting
1. Replace `csr_mcycle` increment with timing-aware function
2. Implement instruction class mapping:
   - Map opcodes to execution classes (ALU, MUL, LOAD, STORE, BRANCH)
   - Apply latency from execution model
3. Add pipeline stall detection:
   - Data hazards (load-use, RAW dependencies)
   - Structural hazards (functional unit conflicts)
   - Branch misprediction penalties
4. Implement memory timing:
   - Cache hit/miss determination based on address patterns
   - Apply appropriate miss penalties
   - Model bandwidth constraints for DRAM

### Phase 3: Power and Energy Tracking
1. Add energy accumulators:
   - Per-instruction dynamic energy
   - State power accumulation over time
2. Implement instruction energy lookup:
   - Map executed instructions to energy values
   - Accumulate total energy in picojoules
3. Add state power modeling:
   - Track time spent in each state (active, idle, sleep)
   - Calculate static energy = power × time

### Phase 4: Event Tracing System
1. Implement trace point enumeration
2. Add conditional tracing based on enabled events
3. Attach contextual information:
   - Program counter (PC)
   - Cycle count
   - Energy delta
   - Memory address (for memory events)
4. Provide callback or logging mechanism for events

### Phase 5: Accelerator Modeling
1. Add accelerator state tracking
2. Implement operation latency and throughput modeling
3. Add energy factors for accelerator operations
4. Provide hooks for accelerator begin/end events

### Phase 6: API Extensions
1. Add functions to:
   - Set/get microarchitecture model
   - Enable/disable event tracing
   - Get current power/energy consumption
   - Get detailed timing breakdown
2. Maintain backward compatibility with existing APIs

## Integration Points in rv32_dpi.c

### Initialization
- Modify `rv_init*` functions to accept optional model parameter
- Add `rv_set_microarchitecture_model` function

### Instruction Execution
- Modify `execute_instruction` and `execute_compressed` to:
  - Determine instruction class
  - Apply timing delays
  - Accumulate energy
  - Generate trace events

### Memory Access
- Enhance `read_u*`/`write_u*` functions to:
  - Check cache hierarchy
  - Apply hit/miss timing
  - Generate memory access events

### CSR Access
- Potentially add new CSRs for:
  - Performance counters
  - Energy registers
  - Model configuration

### Interrupt/WFI Handling
- Update state power modeling during sleep states
- Track idle/sleep state durations

## Profiling Capabilities

With the microarchitecture profile integration, Herve becomes a powerful code profiler capable of:

### Performance Profiling
- Cycle-accurate execution timing per function/basic block
- Instruction mix analysis (ALU, memory, branch ratios)
- Pipeline stall identification (data hazards, structural hazards, branch mispredictions)
- Memory access pattern analysis (cache hit/miss rates, bandwidth utilization)
- Accelerator utilization profiling (for RVV, GEMM, etc.)

### Power/Energy Profiling
- Per-instruction energy breakdown
- Total energy consumption by function/code region
- State power analysis (active vs idle/sleep time)
- Energy-delay product calculations for optimization

### Detailed Tracing and Visualization
- Instruction-level trace with PC, cycle count, and energy
- Memory access traces with address and timing information
- Event timeline generation for Waveshark-like visualization
- Hotspot identification in both time and energy domains

### API for Profiling Tools
- Functions to get execution time/energy for address ranges
- Callback mechanisms for custom profiling tools
- Export capabilities for standard profiling formats (e.g., gprof-compatible output)
- Hardware performance counter-like interface

This profiling capability allows developers to:
1. Identify performance bottlenecks in RISC-V code
2. Optimize for both performance and energy efficiency
3. Validate compiler optimizations and code transformations
4. Profile AI/embedded workloads (GEMM, KV-cache, vector operations)
5. Characterize memory hierarchy behavior
6. Analyze accelerator utilization and effectiveness

### Loading Methods
1. Via environment variable: `HERVE_UARCH_MODEL=model.json`
2. Via API call: `rv_set_microarchitecture_model(model_ptr)`
3. Via firmware embedding (optional)

### Enabling Features
- Set `TRACE_INSNS` for basic instruction tracing (existing)
- Add `TRACE_EVENTS` for microarchitecture event tracing
- Power reporting via new API functions

## Backward Compatibility
- Existing Herve usage without model defaults to:
  - 1 cycle per instruction (current behavior)
  - Zero energy accumulation
  - No event tracing
- **Performance when disabled**: When no microarchitecture model is loaded, Herve operates in high-performance mode with zero profiling overhead, maintaining existing emulation speed
- All existing APIs remain unchanged
- New features are opt-in

## Validation Approach
1. Compare timing results with spike for simple code
2. Validate energy models against empirical data (if available)
3. Test event tracing with known instruction sequences
4. Verify accelerator modeling with vector operation benchmarks

## Dependencies
